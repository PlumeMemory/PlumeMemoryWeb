部署验证

部署是否成功，不应该只看“容器起来了没有”，而是要看关键闭环是否真的能跑通。

推荐验证顺序​

1. 基础健康检查​

确认：

  • API 服务能访问
  • 数据库连接正常
  • 管理员初始化完成

2. 登录或创建 Token​

浏览器工作台应能成功登录，或者控制台可以成功创建一个 CLI / MCP 用的 API Token。这样才能说明认证链路是正常的。

3. 写入一条稳定记忆​

例如写入一条项目约定，然后确认它能在列表或详情页里被看到。

4. 写入一条历史材料​

确认历史层也能正常落库，而不是只有稳定记忆可用。

5. 发起一次任务召回​

使用与刚才写入内容相关的任务描述发起召回，验证 Recall Orchestrator、检索层和结果组装都正常。

6. 执行一次控制操作​

例如删除、归档或切换到临时模式，确认控制管线和权限校验也正常。

推荐自动化脚本​

如果部署仓或服务端仓提供 verify-mvp.sh，应优先把以下场景自动化：

  • 稳定记忆写入
  • 历史材料写入
  • 任务召回
  • 删除
  • 模式切换

这样每次部署后都可以快速确认关键主链路是否仍然可用。

验证结果应关注什么​

重点不是“有没有返回 200”，而是：

  • 返回结果是否符合统一响应格式
  • 写入后的对象是否真能查到
  • 召回结果是否包含预期内容
  • 临时模式是否真的阻断写入
  • 错误信息是否足够明确且不泄露内部细节
